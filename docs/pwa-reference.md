# PWA Reference

BeerJudge is installable as a Progressive Web App. The primary use case is the judging screen: judges install the app on their phone or tablet and can continue filling scoresheets during intermittent connectivity, with IndexedDB backing up in-progress data locally.

---

## What the PWA provides

- **Installable** on Android (Chrome) and iOS (Safari). The OS adds the app to the home screen and launches it in standalone mode (no browser chrome).
- **Offline asset caching** via a service worker. The service worker (generated by `vite-plugin-pwa`) caches JS, CSS, and font files on first load. Subsequent loads serve those assets from cache without a network round-trip.
- The service worker does not cache API responses or page HTML. Scoresheet data that cannot reach the server is held in IndexedDB and retried; this is handled by Alpine.js logic in the judging screen, not by the service worker.

---

## Manifest

Route: `GET /manifest.json` (`branding.manifest`, `BrandingController@manifest`), served as `application/manifest+json`.

| Field | Value | Notes |
|---|---|---|
| `name` | `{CLUB_NAME} BeerJudge`, or `BeerJudge` when `CLUB_NAME` is empty | Full app name shown during installation. |
| `short_name` | `BeerJudge` | Name used on the home screen icon. |
| `description` | `Homebrew competition judging for {CLUB_NAME}`, or `Homebrew competition judging` | Shown in install prompts on some browsers. |
| `start_url` | `/` | URL opened when launching from the home screen. |
| `display` | `standalone` | Hides the browser navigation bar after install. |
| `background_color` | `#1c1917` | Splash screen background (warm near-black). |
| `theme_color` | `#b45309` | Browser UI tint color (amber). |
| `icons[0]` | `/branding/icon-192.png`, 192×192 | Standard home screen icon. |
| `icons[1]` | `/branding/icon-512.png`, 512×512 | High-resolution and maskable icon for Android adaptive icons. |

The manifest is generated per request so it follows `CLUB_NAME`. There is no `public/manifest.json`: nginx serves an existing static file before Laravel, so a file there would shadow the route. `VitePWA` in `vite.config.js` is configured with `manifest: false`.

## Service worker

### Generation

`vite-plugin-pwa` generates the service worker into `public/build/sw.js` during `npm run build`. The Workbox config in `vite.config.js` caches all `*.js`, `*.css`, and `*.woff2` files in the build output:

```js
VitePWA({
    registerType: 'autoUpdate',
    manifest: false,
    injectRegister: null,
    workbox: {
        globPatterns: ['**/*.{js,css,woff2}'],
        navigateFallback: null,
    },
})
```

`registerType: 'autoUpdate'` means the service worker updates itself in the background and activates on the next page load.

`injectRegister: null` disables automatic script injection. Registration is done manually in `resources/js/judging.js`.

### Serving

`vite-plugin-pwa` outputs the SW to `public/build/sw.js`. A service worker can only control pages within its own scope, and the default scope is the directory the SW file is served from. `public/build/sw.js` served at `/build/sw.js` would only control `/build/*` routes, which covers nothing useful.

To give the SW root scope, a Laravel route re-serves it at `/sw.js` with a `Service-Worker-Allowed: /` header:

```php
// routes/web.php
Route::get('/sw.js', function () {
    $path = public_path('build/sw.js');
    abort_if(! file_exists($path), 404);

    return response(file_get_contents($path), 200, [
        'Content-Type' => 'application/javascript',
        'Service-Worker-Allowed' => '/',
        'Cache-Control' => 'no-cache, no-store, must-revalidate',
    ]);
});
```

`Cache-Control: no-cache` ensures the browser always checks for a fresh SW, which is how `registerType: 'autoUpdate'` works in practice.

### Registration

`resources/js/judging.js` registers the SW after the window `load` event:

```js
if ('serviceWorker' in navigator) {
    window.addEventListener('load', () => {
        navigator.serviceWorker.register('/sw.js', { scope: '/' }).catch(() => {})
    })
}
```

The `scope: '/'` combined with the `Service-Worker-Allowed: /` header gives the SW control over all routes. `judging.js` is only loaded on the judging page, so the service worker is registered the first time a member opens a judging screen.

## Icons

Source SVG: `resources/images/icon.svg` (amber pint glass on a `#1c1917` background). This is the neutral default.

Output files (the defaults):
- `public/icons/icon-512.png`
- `public/icons/icon-192.png`
- `public/favicon.svg` (copied from source)

To regenerate after editing the source SVG:

```bash
convert -background '#1c1917' resources/images/icon.svg public/icons/icon-512.png
convert public/icons/icon-512.png -resize 192x192 public/icons/icon-192.png
cp resources/images/icon.svg public/favicon.svg
```

Requires ImageMagick (`convert`).

### Club icons

`GET /branding/{file}` (`branding.icon`) serves `icon-192.png`, `icon-512.png` and `favicon.svg`. When `CLUB_ICON_DIR` names a directory that holds the requested file, that file is served; otherwise the default above. Each file falls back on its own, so a club can override only the favicon. Other file names return 404.

To brand an instance, put the three files in a directory the app can read and set `CLUB_ICON_DIR` to its absolute path. In the Docker image the repository sits at `/var/www`, so icons committed under `resources/branding/<club>/` are reachable as `/var/www/resources/branding/<club>`; icons kept outside the repository need a volume mount.

`resources/branding/foebar/` holds the Foebar Amsterdam Homebrew Group's icons (pint glass with the Amsterdam arms) and logo.

The standalone error views link the default files directly (`/icons/icon-192.png`, `/favicon.svg`), so they do not depend on the app being able to serve a request.

## PWA meta tags

All full-page Blade views include PWA meta tags via the `<x-app-head />` component. The tags reference the manifest route, the `branding.icon` routes for the touch icon and favicon, and the theme color.

Any new Blade view that renders a complete HTML document must use `<x-app-head />` (or include equivalent tags). Error views (`resources/views/errors/`) are standalone and include the tags directly.

## Browser support

| Browser | Install | Service worker |
|---|---|---|
| Chrome (Android, desktop) | Yes, via browser install prompt | Yes |
| Safari (iOS 16.4+) | Yes, via Share → Add to Home Screen | Yes (iOS 16.4+) |
| Firefox (Android) | Yes | Yes |
| Safari (macOS) | No install prompt | Yes |

iOS Safari does not show a banner install prompt; users must manually add to home screen via the Share menu. iOS 16.3 and earlier have limited service worker support.
