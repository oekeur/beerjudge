# Judging

The judging screen is a Blade page with Alpine.js. Judges score entries on the BJCP 50-point scale. Each sheet saves to IndexedDB on the judge's device as it's filled, then syncs to the server — so a dropped request, a sleeping phone, or an accidental refresh doesn't lose in-progress work.

## Data model

**`scoresheets`**

| Column | Type | Notes |
|---|---|---|
| id | bigint | PK |
| entry_id | bigint | FK → entries |
| judge_id | bigint | FK → members |
| aroma | integer | 0–12 |
| appearance | integer | 0–3 |
| flavour | integer | 0–20 |
| mouthfeel | integer | 0–5 |
| overall | integer | 0–10 |
| total | integer | Computed: sum of the five scores |
| aroma_notes | text | nullable |
| appearance_notes | text | nullable |
| flavour_notes | text | nullable |
| mouthfeel_notes | text | nullable |
| overall_notes | text | nullable |
| descriptors | json | Array of descriptor slugs (see below) |
| client_uuid | char(36) | Client-generated UUID; used for upsert idempotency |
| status | enum | `draft`, `submitted` |
| submitted_at | timestamp | nullable; set on first submission |
| timestamps | — | created_at, updated_at |

**Unique constraint:** `(entry_id, judge_id)` — one scoresheet per judge per entry.

## Judge pool

Judging is an open pool — no pre-assignment of judges to entries. Any registered judge can score any entry except their own (`entry.member_id != judge_id`). There is no minimum judge count per entry.

## Judge self-registration

Members opt in to judging a competition explicitly.

`POST /competitions/{competition}/judges` — registers the current member as a judge (adds to the `competition_member` pivot).
`DELETE /competitions/{competition}/judges` — deregisters.

The judging screen also auto-registers a member as a judge the first time they load it for a competition.

The admin can also share a **judge participation link** (generated in the Filament Competition > Judging tab) to invite members to register as judges.

## Offline-first sync

The judging screen uses Alpine.js for interactivity and IndexedDB (via Dexie) for local storage. The flow:

1. Judge opens the judging screen. Entry list is server-rendered into the page on load (no separate API call).
2. As the judge fills a scoresheet, Alpine writes the current state to IndexedDB using a `client_uuid` generated by the client.
3. Alpine POSTs to `POST /scoresheets`. If the post fails, the sheet stays in a queued state and retries automatically.
4. On success, the server returns `{ id, client_uuid, status, saved_at }`. The local state transitions from `draft` to `submitted`.
5. A submitted sheet can be reopened and resaved. The same `client_uuid` is used, so the server upserts the existing row rather than creating a duplicate.

The session cookie covers the judging route — no separate API token.

## Scoresheet endpoint

`POST /scoresheets` — accepts a single sheet or a queued batch. Validates via `StoreScoresheetRequest`. Upserts by `client_uuid` (or falls back to `(entry_id, judge_id)` on conflict). Returns JSON.

Constraints enforced server-side:
- Competition must be in `judging` status.
- Judge cannot score their own entry.
- Score values must be within their category maximum.

A submitted sheet can be resaved (same `client_uuid`) until the competition moves to `closed`.

## Off-flavor descriptors

Judges can tag off-flavor descriptors on each scoresheet. The 17 supported slugs:

`acetaldehyde`, `alcoholic`, `astringent`, `diacetyl`, `dms`, `estery`, `grassy`, `light_struck`, `metallic`, `musty`, `oxidized`, `phenolic`, `solvent`, `sour_acidic`, `sulfur`, `vegetal`, `yeasty`

Descriptors are stored as a JSON array of slugs in the `scoresheets.descriptors` column. The valid slug list lives in `ScoresheetController::descriptorSlugs()`.

**Deviation from enhancement PRD:** the enhancements PRD specified a `descriptors` reference table and a `scoresheet_descriptor` pivot with optional intensity. The implementation uses a JSON column instead — simpler, no join required at this scale, and intensity is not implemented.

## Style guidelines panel

Each entry on the judging screen has a collapsible panel showing the BJCP style guide for that entry's style: overall impression, aroma, appearance, flavor, mouthfeel, vital-stat ranges (OG, FG, ABV, IBU, SRM), and commercial examples. Content is server-rendered into the page on load — available without a live connection.

## PWA install

The judging screen is the primary target for PWA install — judges add it to their home screen and use it as a standalone app on their phone or tablet.

**Manifest:** `public/manifest.json` — name "Foebar BeerJudge", short name "BeerJudge", `start_url: /judge`, display `standalone`, theme `#b45309`, background `#1c1917`.

**Icons:** `public/icons/icon-192.png` and `public/icons/icon-512.png` — Amsterdam coat of arms (three St Andrew's X marks) inside an amber pint glass on a dark background. Source SVG at `resources/images/icon.svg`.

**Service worker:** generated by `vite-plugin-pwa` (Workbox), emitted to `public/build/sw.js`. Served at root scope via `GET /sw.js` in `routes/web.php` with `Service-Worker-Allowed: /` header. Registered manually in `judging.js` as `navigator.serviceWorker.register('/sw.js', { scope: '/' })`.

**Scope fix rationale:** `laravel-vite-plugin` places build output in `public/build/`, limiting a SW there to the `/build/` scope. The Laravel route re-serves it from `/sw.js` with a header granting root scope, so the SW can control `/judge`.

**PWA meta tags** are encapsulated in the `<x-app-head>` anonymous Blade component (`resources/views/components/app-head.blade.php`). Any new view rendering a full HTML document must use `<x-app-head>` in its `<head>` block rather than inlining these tags.

The judging view uses `<x-app-head :vite="['resources/css/app.css', 'resources/js/judging.js']">` and passes the CSRF token meta and Sentry DSN/user meta tags via the component slot.

## Out of scope

Pre-assignment of judges to entries. Minimum judge count enforcement. Judge anonymity from each other. Score normalization or outlier removal. Livewire (deliberately excluded — would re-render on every keystroke and lose in-progress input on a network blip).
